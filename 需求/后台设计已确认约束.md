### 版本与算法归属（2026-09-16 用户明确）

**用户决定：「`growth_v1` / `pw_v1` 都由 DingDong 侧定义」——我们（CA）只消费。**

| 版本标识 | 对应字段 | 归属 |
| --- | --- | --- |
| `growth_v1` | `growth_period.algorithm_version` | **DingDong 侧定义** |
| `pw_v1` | `persona_public_view.talent_weight_version` | **DingDong 侧定义** |

1. 我们在响应里拿到并存储/展示这两个版本号，**不自行定义、不自行实现、不得改名**。
2. 人设清单（`persona_name` / `persona_type` / `public_description` / `learning_style_tags` / `talent_weight_version`）同样由 DingDong 维护，我们通过 `GET /api/v1/ca/persona/current` 与 `persona_public_view` 读取并展示；对方若扩充 `persona_type`，我们需能容错未识别值。
3. 八维 `growth_dimensions`、`match_score`、`health_score` 全部由对方产出，**我们不产出这些分数**——因此既有 demo 边界「探索体验不产出天赋或能力分数」**无需松动**（第一版曾误记为"要我们产出"，已更正）。
4. 复测触发 H01–H07 与阈值参数由对方（Health Engine）实现，我们只按返回的 `status` / `reassessment_recommended` 做界面反应。
5. 原先"画像更新规则由谁提供尚未明确、不默认由我们设计"的保留意见**成立且已明确**：既不由我们设计，也不由我们实现。
6. 版本标识是对外契约的一部分：升级策略（旧 `growth_period` 是否仍可查、同一周期出现多个算法版本时如何展示）需向 DingDong 确认。

### 仍然待澄清的事项

**向 DingDong 侧（20 问，见[影响分析](../需求/CA对接文档V1.0_影响分析_20260916.md)第 5 节；**已整理成可直接发出的清单**：[CA-DingDong 对接澄清清单 V1.0](../需求/CA-DingDong_对接澄清清单_V1.0_20260916.md)，含优先级与回复模板）**：两份材料口径统一（接口 8/7、实体 6/7）、唯一错误码表与 `message`/`request_id` 幂等约定、**首次测评画像的提交通道（接口清单里缺失，最大缺口）**、`reassessment/current` 空数据时的返回码、`period=15d|30d` 窗口口径、`switch_candidate`/`keep_current` 由哪个字段表达、`X-API-Key` 签发与 `mock`/`production` base URL、Mock 环境归属、xlsx 里 datetime 示例为日期序列号、`interest_*` code 表、`persona_type` 扩充策略、版本升级策略，以及因 C1 定案新增的 **D18 机器人标识与 token 生命周期、D19 `ca_account_id` 格式可接受性、D20 换绑时对方侧 binding/成长数据处置**。

**我们自己的决定（2026-09-16 已定案）**：`ca_account_id` 的形态——**账户级，一台机器人一个号**（用户原话：「账户级就可以了　一台机器人一个号」）。即：不设家庭级聚合层；机器人 : `ca_account_id` = 1 : 1；取值 `ca_` + 26 位 ULID；首次绑定前由我们生成，一经生成**永不修改、永不回收重用**（解绑后置 `retired` 归档）；跨设备稳定（不绑手机号/登录会话/设备指纹）；按不透明字符串对外。完整规格（含落库表 `CaAccount`、与 `Family`/`Child`/`ProfileSnapshot` 的映射、换机语义与给对方的 D18–D20）见 [`设计/CA对接_C1_ca_account_id设计_20260916.md`](../设计/CA对接_C1_ca_account_id设计_20260916.md)。

**同日追加定案 2 项（决定 schema 最终形状）**：① **一台机器人服务一个孩子**——`child` 为必填 FK，账户 : 孩子 = 1 : 1（对方匹配的输入是画像，画像在我方按 `child` 存，一号多孩会使 `persona`/`growth_period` 失去归属）；② **换机发新号**——换一台机器人即换一个新 `ca_account_id`，旧号置 `retired` 归档、永不重用，号码跟机器走不跟孩子走。**已知代价**：换机后对方侧 `growth_period` / `reassessment_event` 无法延续，成长报告会重新开始；缓解措施为换机前确认弹窗 + 我方保留旧号只读历史入口 + 旧号永久保留不删除（见该文 §5 ②）。**「一台机器人一个号」按字面严格执行：同一台机器人终身同一个号，换机就是换号。**

## 指纹图片一次性处理，不留存

用户明确：指纹图片仅作一次性处理，不留存。撤销此前将指纹图片放入对象存储的建议；不在PostgreSQL保存图片或图片存储地址。

正式实现须满足以下约束：

- 前端图片仅用于当前采集/处理过程，不写入localStorage、IndexedDB、持久缓存或导出文件。用户从相册选择的原文件不属于应用新增副本，不自动删除用户原文件。
- 处理结束、取消、退出采集或超时后释放应用持有的图片、预览和摄像头资源；重试可要求重拍，不以恢复进度为由保存图片。
- 如算法调用需要经CA后端中转，只允许有大小和时间上限的临时内存处理。实现时须检查框架上传处理、反向代理请求缓冲，防止自动写入临时文件。
- 图片、base64内容及可重建指纹的模板不进入数据库、对象存储、任务队列、日志、错误追踪、调试抓包文件或备份。算法调用采用有界请求处理，不能把图片放进持久任务等待重试。
- 数据库可保留采集/测评任务状态、时间、版本及必要错误码。问卷和获准保存的业务结果按自身的数据规则处理；算法输出若包含生物特征模板，不能以“结果”名义留存。
- 甲方算法是否需要原图、能否一次性处理且不保存、是否在日志或训练中使用，属于接入前必须核实的契约。当前不能宣称外部算法已满足这些要求。

五枚指纹是输入流程，不意味着建立五枚图片档案。页面刷新后可恢复非图片业务进度，但临时图片需重新采集；不能承诺同时“不留存图片”和“跨会话恢复图片”。
