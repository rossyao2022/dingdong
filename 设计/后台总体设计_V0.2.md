# 后台总体设计 V0.2：脚手架与一期菜单权限

> 文档状态：历史设计基线，保留当时的建议与判断，不能把下文“当前/尚未实现”当作现状。2026-09-12 已有 M1–M5 实现；当前入口见 [文档索引与当前状态](../文档/文档索引.md)，实际字段见 [模型字段清单](数据库实际字段_M5.md)。外部供应商尚未接入。

状态：设计方案，尚未实现。用户接受以成熟开源脚手架二次开发的建议；本版以 Cookiecutter Django 为首选底座、Django Admin 为一期内部入口继续设计。具体依赖版本和生成选项在最小工程验证后锁定，不等于已完成脚手架运行验证。本文替代 V0.1 的技术骨架、菜单权限和任务实现建议；未改动的业务流程与指纹不留存要求继续有效。

## 1 技术底座与复用边界

采用 Python＋Django＋DRF＋PostgreSQL 的模块化单体。家长端继续接入业务 API；内部后台使用 Django Admin，并为发布、重试等流程增加专用操作页。暂不并行建设 Vue 管理后台，也不混合两套脚手架。

| 能力 | 一期处理 |
| --- | --- |
| 工程配置、数据库迁移、测试、Docker | 复用 Cookiecutter Django；固定上游提交和生成参数，保留许可证与来源记录 |
| 用户模型 | 首次迁移前扩展脚手架自定义用户；区分家长账号与工作人员账号，工作人员资格不可由公开接口赋予 |
| 家长登录 | 手机短信＋Simple JWT，按现有登录设计补充刷新、撤销和限流；不开放脚手架默认邮件注册/密码找回给家长 |
| 内部登录 | 独立工作人员入口，Django 会话＋CSRF；一期采用 Django 密码登录、登录限频，无公开注册；TOTP 暂缓。家长 JWT 不能进入 Admin |
| 后台权限 | Django Group＋Permission，固定角色初始化；业务层统一校验，不另造权限平台 |
| 内部管理界面 | 复用列表、筛选、分页；结果只读，关键操作走服务函数，禁止直接改状态字段 |
| 异步处理 | 优先验证脚手架的可选 Celery 路径，拟配 Redis 作消息代理；替代 V0.1 自研数据库队列的优先建议 |
| 业务与外部协议 | 家庭归属、问卷版本、结果、报告和 DingDong 适配独立开发 |

Redis 不保存业务真相。PostgreSQL 的 BackgroundJob 保存业务状态，Celery 消息只放任务 ID。事务提交后投递，定时扫描到期 pending 任务补投；worker 原子领取并做业务幂等，完成结果时检查当前执行代号。复用任务表恢复投递，不另建 outbox 或派发状态机。一次性图片仍走有界同步内存通道，不进入 Celery。

以上 Redis/Celery 与后台认证为本版设计建议，尚未部署或开通任何供应商服务。

## 2 菜单做减法：五个入口

| 一级入口 | 页面与最小展示 | 允许的业务操作 |
| --- | --- | --- |
| 家庭档案 | 家长脱敏手机号、儿童别名/必要年龄信息、授权状态、外部关联验证状态 | 按家庭 ID 或精确手机号定位；记录服务处理事项。不可人工强制把未验证设备改为已验证 |
| 测评与报告 | 测评时间与版本、完成进度、算法状态、报告版本和状态、网页活动完成记录 | 查询必要摘要；在条件满足时重新生成报告。原始答案、详细画像不默认展示 |
| 数据同步 | 最近成功时间、同步窗口、失败原因、任务尝试记录 | 技术人员暂停/恢复关联的同步、重试可重试任务；无授权或未验证关联不能强行重试 |
| 内容与规则 | 题库、网页活动内容、报告模板、已接入规则的版本和发布状态 | 编辑草稿、校验、发布、停用；已发布内容不可原地修改。规则仅接入甲方明确提供的方案 |
| 系统管理 | 工作人员、固定角色分配、脱敏审计、数据处理请求 | 停用账号、撤销登录、分配预设角色；数据处理请求按受控流程执行 |

不单独建设首页大屏、任务中心、孩子管理、设备管理和报告中心等重复入口。任务详情从对应业务记录进入；孩子放在家庭详情；外部关联放在家庭详情；报告放在测评与报告。技术任务如报告生成失败也可从任务关联页定位，避免只有同步任务可排障。

数据处理请求记录对象、请求类型、核验状态、处理结果与必要原因；不提供通用表删除器。删除执行规则和保留期限需在正式处理前明确。

菜单以代码声明，按当前工作人员权限显示。一期不提供菜单配置 CRUD 或拖拽编辑器。五个入口是产品分组，Django Admin 的模型注册和 app 分组按此裁剪，不把所有数据库表自动暴露出来。

## 3 固定角色：三类业务角色＋账号管理员

家长属于家长端身份，不属于后台角色。一个工作人员可兼任多个固定角色；权限取并集，但仍受对象范围、字段输出及业务状态约束。

| 能力 | 运营支持 | 内容负责人 | 技术运维 | 账号管理员 |
| --- | --- | --- | --- | --- |
| 家庭及测评状态 | 脱敏查询 | 不开放个人记录 | 仅内部 ID 与技术状态 | 默认无权限 |
| 报告 | 必要状态及摘要 | 仅合成样例预览 | 生成状态、错误码 | 无 |
| 题库/模板/规则版本 | 只读版本说明 | 草稿、校验、发布、停用 | 只读技术版本信息 | 无 |
| 同步/任务 | 只读状态 | 无 | 查看、暂停、恢复、合规重试 | 无 |
| 工作人员和角色 | 无 | 无 | 无 | 创建/停用工作人员、分配固定角色 |
| 审计 | 自己的服务操作 | 自己的内容操作 | 技术操作 | 账号和角色变更 |
| 数据处理请求 | 登记与查询进度 | 无 | 执行已确认归属且规则明确的任务 | 无 |

账号管理员不等于 Django superuser，不自动获得业务读取权；不能修改预设角色的权限集合、赋予 superuser 或编辑自身角色。其初始化和权限变更通过受控运维流程完成，管理页面仅允许为其他工作人员分配预设业务角色。

Django superuser 只用于初始化或应急维护，不作为日常角色。它在框架层有高权限，不能宣称同样受普通角色限制；使用须受控并记录。数据库运维权限也不能靠应用菜单限制。

一期不默认开放完整问卷、完整手机号、批量导出、代家长登录或人工修改评分。若实际客服需要读取详细报告，后续增加明确的查看能力及访问理由，不直接扩大运营组的全部模型权限。

## 4 权限保留什么，删掉什么

### 保留三层判定

1. 身份：家长 JWT 校验账号和登录授权；工作人员会话校验账号有效、staff 资格与入口要求。
2. 动作：普通查询采用明确的查看权限；发布内容、重试任务、管理工作人员、执行数据处理分别定义业务权限。拥有查看权限不代表允许变更。
3. 数据范围：家长只能访问当前有效归属的儿童及其数据；工作人员按角色返回最小字段。业务授权撤回、设备解绑、任务失效等状态可进一步拒绝操作。

固定权限示例：`view_family_summary`、`view_assessment_status`、`view_report_summary`、`publish_content`、`retry_job`、`manage_staff`、`execute_data_request`。名称在实现时按 app 规范落定。菜单和按钮引用相同动作权限，不再维护第二套菜单授权表。

家庭一期建议一个儿童仅对应一个有效归属家庭，由一个家长账号管理；保留独立 Family/FamilyMembership 关系，为以后家庭成员扩展提供迁移空间，一期不做邀请、共享和转移界面。此处为建模建议，并非用户已确认开放多人共同管理。

### 暂不建设

- 部门、岗位、组织树、企业租户、机构数据范围。
- 自定义角色编辑器、逐用户权限特例、动态菜单和字段权限配置平台。
- 通用审批流、工作流设计器、插件市场、代码生成器界面。
- 通用文件库、任意 SQL/脚本执行、接口白名单编辑器。
- 设备下发控制、机器人任务推送、CA 入站机器人接口。

字段脱敏与最小输出仍然必须实现，只是通过明确的角色输出结构实现，不给运营人员提供任意字段授权界面。题库和模板等业务配置也继续保留，不因删掉通用配置中心而硬编码业务内容。

## 5 后端落点与容易遗漏的路径

Django 默认模型权限与用户组可以复用，但不自动完成本项目家庭隔离。DRF 列表查询须按归属过滤；详情、创建、关联字段和批量动作也要独立检查。不能只在取单条记录时调用对象权限检查。

- 家长端：从当前身份确定家庭范围，忽略客户端试图指定的 owner；报告、答案、测评等通过儿童归属过滤。跨家庭对象统一返回不泄露存在性的响应。
- Admin：定制 queryset、只读字段、对象权限和动作；关联选择框、自动补全、搜索、历史页面、预览同样限制字段与范围。技术角色不能通过关联链接跳到个人资料。
- 业务服务：API、Admin 动作、定时任务共用状态与授权校验。接口不能因为隐藏了按钮就跳过授权。
- 后台任务：执行前和保存前重查有效授权与关联；人工触发任务再次核查请求人权限。系统调度使用明确系统身份和相同业务约束。
- 数据输出：手机号脱敏、儿童用内部 ID/别名，技术日志仅必要错误码和追踪号。审计记录操作者、动作、对象 ID、结果、时间及允许的原因，不记录整份请求正文。
- Admin 默认操作日志不足以覆盖敏感读取和所有业务操作；补充 AuditEvent。审计在应用层只追加，后台无编辑/删除入口。
- 指纹通道：不注册任何图片模型或文件管理入口，禁用相关请求体记录与磁盘上传回退。指纹结果仍按白名单保存，不能借通用 JSON 字段保存生物特征模板。

内容版本建议采用草稿→发布→停用的固定状态，发布时即时校验。校验只覆盖格式、必填项与合成样例，不代替甲方对算法/评分方法的确认。发布权限由内容负责人持有；一期不做通用多级审批。旧会话固定引用旧版本，停用仅阻止新会话选用，不抹除历史依据。

## 6 实施顺序与验证门槛

第一步：生成隔离的最小 Cookiecutter Django 工程，锁定 Python/Django/DRF/Simple JWT/数据库驱动的兼容版本；验证 PostgreSQL 迁移、测试和部署，不导入真实家庭材料。

第二步：先完成用户模型、家长登录、工作人员入口、固定角色及五个菜单空壳。用两个虚构家庭、各角色账号验证权限。此时再确定 Admin 定制工作量是否合理；若运营流程大量依赖跨表专用页面，再评估独立前端，不预先双轨建设。

第三步：实现问卷与结果版本、DingDong 适配器和任务运行层。对外协议未定部分仅用明确标记的模拟数据，不虚构正式字段。

第四步：接入甲方算法和真实 DingDong 契约，再验证指纹全链路不留存、重复执行幂等和授权撤回。未确认无留存算法契约前不启用真实指纹上传。

核心验收：直接访问隐藏菜单 URL 仍拒绝；列表/详情/关联选择/新建/批量请求无跨家庭泄露；低权限账号不能授予自己权限；停用或撤销登录后失效；内容负责人不能读取真实儿童问卷；技术运维不能读取报告正文；重复重试不重复记分；授权撤回后任务不保存新数据；指纹在成功/失败/超时路径均不进入磁盘、日志、队列和备份。

## 7 尚待外部明确的内容

DingDong 的身份对应、字段与频率；甲方算法输入与无留存契约；成长评分更新规则及责任方仍待确认。这些不阻止账号、菜单和权限建设。正式工作人员名单、短信供应商和数据处理期限在对应功能接入前落实，一期菜单不需要因此扩充。
