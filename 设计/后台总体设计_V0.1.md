# 后台总体设计 V0.1

> 文档状态：历史设计基线，保留当时的建议与判断，不能把下文“当前/尚未实现”当作现状。2026-09-12 已有 M1–M5 实现；当前入口见 [文档索引与当前状态](../文档/文档索引.md)，实际字段见 [模型字段清单](数据库实际字段_M5.md)。外部供应商尚未接入。

> 后续版本：[V0.2：脚手架与一期菜单权限](../设计/后台总体设计_V0.2.md)。技术骨架、菜单权限、任务实现建议以V0.2为准；本版保留业务流程说明。

本文继续细化一期后台，作为讨论和后续实现的设计基线，不代表已经实现。用户已确定Python＋PostgreSQL；以下框架及运行方案为推荐方案。业务边界以[后台设计已确认约束](../需求/后台设计已确认约束.md)为准。

## 1 技术骨架

建议使用Django＋Django REST Framework，采用模块化单体。Django Admin提供初期运营操作入口；家长端继续使用现有Web，逐步由正式API替换本地演示存储。暂不以换前端框架作为开工前提。

| 层 | 推荐方案 | 职责 |
| --- | --- | --- |
| Web API | Django＋DRF | 身份、业务校验、权限、采集会话、报告查询 |
| 业务数据库 | PostgreSQL＋Django ORM | 关系、状态、结果版本和持久任务 |
| 后台任务 | 同一代码库的独立worker进程 | 主动获取DingDong数据、处理已获准保存的数据、生成报告 |
| 定时调度 | 调度进程向数据库写任务 | 到期数据获取；与worker分开启动 |
| 运营入口 | Django Admin＋必要的专用操作页 | 查询、审核、重试及审计 |
| 外部调用 | 独立算法适配器、DingDong适配器 | 隔离外部协议和内部业务对象 |

一期先用PostgreSQL任务表，不额外引入Redis、Celery和消息中间件。任务记录只放对象ID、任务类型和运行状态，不放指纹图片或任意请求正文。若后续任务规模需要更成熟的队列体系，再替换运行层，业务流程不随之重写。

建议前后端同域部署。用户已确认家长使用手机号＋短信验证码登录，随后使用JWT访问业务API，不建立独立孩子登录。访问令牌与刷新令牌分开，具体存放、刷新及撤销方案见[登录认证设计](../设计/登录认证设计_V0.1.md)。后台工作人员使用独立权限组和加强认证，不能因为属于staff就默认可查看全部敏感业务资料；Django Admin的工作人员认证与家长JWT登录分开设计。

## 2 五个业务模块

### 用户与档案

家长身份、孩子档案、授权记录，以及孩子与DingDong外部标识的对应关系。所有用户请求由服务端验证归属，不信任前端传入的parent_id。首期界面可先做单孩子档案，但数据关系支持一个家长对应多个孩子；实际开放数量仍待确认。

手机号只负责登录，不直接当作跨平台共享标识。NFC负责进入来源，不能单凭URL参数证明设备归属。DingDong未给出可靠对应机制前，设备关联保持未验证状态，不获取并归档该设备数据。

### 测评

管理题库版本、答题会话、甲方算法调用状态及初始结果。问卷进度可保存；图片只在本次处理期间存在。重进页面可恢复问卷，不能恢复上次图片。算法输入、手指槽位和正式题量通过甲方规则配置，不把当前四题演示当成正式题库。

### 机器人数据

CA后台主动调用DingDong服务。接入过程为：确定允许查询的对象和时间范围→获取→字段白名单校验→归属与重复校验→保存允许的数据→推进同步进度。没有面向DingDong的入站API，不发送画像、策略或机器人任务。

### 画像与报告

分别维护初始测评结果、机器人行为观察、按规则产生的阶段画像，以及家长报告。报告引用确定的结果和数据版本；后续数据补齐后生成新版本，不静默修改旧报告。没有评分更新规则时可以形成行为观察，评分更新任务保持“等待规则”，不自行加减专业分数。

### 运营与治理

一期提供“查家庭与档案、查测评、查同步、查报告、查任务”五个入口。运营人员看到状态、原因及必要摘要；审核人员维护规则和内容版本；技术人员处理同步故障。重试、取消、修订和数据处理请求通过业务操作执行，不直接任意改生产表。

## 3 数据库的大方向

关系、归属、时间、状态和版本使用明确字段；供应商差异化结果采用经过白名单筛选的JSONB。JSONB不是保存所有原始响应的兜底仓库。

| 数据组 | 主要实体 | 保存什么 |
| --- | --- | --- |
| 身份与归属 | Parent、Child、Consent | 登录身份、档案、授权用途/版本/时间 |
| 外部关联 | ExternalAssociation | 孩子、供应商标识、验证状态、有效起止时间 |
| 测评过程 | AssessmentSession、Answer、AlgorithmAttempt | 固定题库版本、答案、处理状态、请求号、算法版本、必要错误码 |
| 初始和阶段结果 | ProfileSnapshot | 结果类型、各维度、规则版本、来源依据、形成时间 |
| 外部观察 | ObservationBatch | 孩子、粒度、时间窗口、供应商版本、白名单结果、接收时间 |
| 同步进度 | SyncCheckpoint | 对象、游标或上次成功窗口、最近成功时间、状态 |
| 报告 | ReportVersion | 引用的画像和观察版本、模板版本、报告内容及修订原因 |
| 可靠运行 | BackgroundJob、AuditEvent | 对象引用、重试/租约、操作人与结果 |

这些是概念实体，不要求每个都对应独立服务。事件明细是否需要单独建表，取决于DingDong是否真的提供事件；不同时默认建设事件和聚合两套管线。所有图片字段、图片URL、指纹base64、生物特征模板均不进入模型。

所有时间按有时区时间保存，业务展示默认Asia/Shanghai。15/30天只是此前候选观察窗口，不等于已确认回测周期。零、缺失、未授权、获取失败分别处理。

## 4 三条主要处理流程

### A 一次性指纹处理

默认按“Web→CA临时处理通道→甲方算法→返回允许保留的结果”设计，算法密钥仅在服务端。前提是甲方支持不保存输入的处理模式；不支持时不得通过增加临时对象存储绕过约束。

1. 先登录、验证孩子归属和授权，保存问卷与测评会话。
2. 图片在浏览器内采集和预览。本次提交携带会话及业务请求号，后端验证状态后进行有界内存处理。
3. 限制单图、总请求体、并发、图片解码尺寸和处理时间，避免内存耗尽。具体上限须由甲方合格样例及压测确定，不能直接把演示的10MB上限乘以五当作生产配置。
4. 使用专门的内存上传处理路径，禁用上传临时文件回退。检查代理、应用服务器、框架、中间件及监控链路；不能只检查业务代码是否调用save。
5. 调用算法不跨越长数据库事务。先以短事务登记处理中，调用结束后再次检查归属、授权与结果合法性，再原子保存允许的结果和状态。
6. 请求结束或取消时释放图片引用与摄像头资源。后台任务只拿结果ID生成报告，不拿图片。

算法超时后记录“结果未知”或“需重新采集”。如对方支持按请求号查询，查询结果时无需保留图片；否则需要用户重新采集。不能后台悄悄重新上传，也不能宣称数据库幂等就保证供应商没有重复执行。处理进程崩溃后只恢复业务状态，不恢复图片。

数据库不保存图片不等于图片全链路不落盘。部署验收还须核查请求日志、异常上下文、代理缓冲、临时目录、swap和崩溃转储；不对语言运行时作“立即物理擦除内存”的保证。

### B 主动获取DingDong数据

定时调度为已验证且有授权的关联创建获取任务；运营端可触发一次人工刷新，相同对象和范围的任务合并或去重。具体调度周期待对方频率与限额明确后配置，生产初始不启用猜测的周期。

worker用短事务领取任务，网络调用在事务外完成。验证结果后，在同一事务内写入观察批次并推进游标；失败不能先推进游标。重复批次不重复计数；同一上游版本内容冲突进入人工核查。撤回授权后停排新任务，并在任务执行前和保存前重新检查。

取回的是聚合快照时按窗口/版本保存，不把滚动快照逐次相加。迟到或修正数据建立修订并触发相应报告更新。拿不到数据时保留最后成功更新时间和失败状态，不把失败解释成孩子没有参与。

### C 阶段画像与报告

新观察批次→行为指标整理→按已发布规则生成画像版本→生成家长报告。无可用规则时，先完成行为观察，保留待评分状态。

每个阶段结果引用输入观察批次和规则版本，每份报告再引用结果及模板版本。规则升级或补数产生新修订，并保留原因。重跑同一输入和版本不重复生成相同结果。初始测评结果保持独立，不能被滚动成长评分覆盖。

## 5 后台任务的可靠性

任务状态至少为待执行、执行中、等待外部条件、结果未知、成功、失败和取消。任务有唯一业务键、最大尝试次数、下次执行时间以及执行租约。worker崩溃后，过期租约可以重新领取；执行结果用租约标识校验，旧worker不能覆盖新执行。

默认按“至少一次执行＋业务幂等”设计，不承诺恰好一次。PostgreSQL的SKIP LOCKED适合多个消费者领取队列记录；它不代替任务租约、超时恢复或业务去重。[PostgreSQL SELECT文档](https://www.postgresql.org/docs/current/sql-select.html)

观察写入、任务完成和需要生成的下一步任务在同一数据库事务中提交，避免数据保存成功却没有报告任务。单靠内存回调或进程消息不足以保证这一点。外部HTTP调用不放在持锁事务里。[Django事务文档](https://docs.djangoproject.com/en/5.2/topics/db/transactions/)

## 6 API和后台页面边界

CA会提供供自己Web调用的API；“不提供API给DingDong”不意味着CA没有后端接口。

- 身份与档案：发送验证码、登录退出、当前家长、孩子档案、授权管理。
- 测评：创建会话、保存答案、提交一次性采集、查询处理状态和初始结果。
- 成长：查询观察批次、阶段画像、报告版本及同步状态。
- 运营：查看任务、触发允许的重试、审核发布规则/模板、查询审计记录。

本轮先确定这些能力，不虚构DingDong URL和字段。甲方算法与DingDong分别使用适配器，响应经白名单转换为内部对象。不得将外部原始响应直接写日志或自动存JSONB，尤其不能保存夹带的图片/特征模板。

## 7 验收与下一轮需要敲定的事

第一批验证应覆盖：两个家庭隔离；同一孩子刷新恢复问卷；图片成功、失败、超时、取消路径均不落盘；重复提交不重复建结果；worker崩溃能恢复；分页失败不前移游标；撤回后不入新数据；重复快照不累加；补数生成报告修订；规则缺失不生成假分数。

图像验证使用合成图片，检查部署链路的临时文件、日志、队列和数据库；不能只根据前端“未上传”文案或单元测试判断生产环境不留存。Django默认上传处理包含内存和临时文件两种处理器，大文件会写临时文件，因此必须替换相关默认路径。[Django上传文档](https://docs.djangoproject.com/en/5.2/topics/http/file-uploads/)

Nginx如用于代理，须明确检查请求缓冲行为；关闭proxy_request_buffering也不能自动证明其余链路不写文件。[Nginx请求缓冲文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_request_buffering)

接下来内部只需先讨论三个选择：是否采用Django＋DRF；是否接受Admin作为首期运营入口；是否接受PostgreSQL任务表＋独立worker作为首期异步方案。

外部仍有三项依赖：DingDong身份对应及实际数据契约；甲方算法一次性图片处理契约；行为如何更新画像评分及其规则责任。它们不阻止内部数据模型和账号后台设计，但会影响正式采集、同步和评分模块的最终实现。
