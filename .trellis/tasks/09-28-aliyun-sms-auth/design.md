# 设计

## 产品选择

Seewow 的 `aliyunVerifySms.ts` 使用号码认证 `Dypnsapi/SendSmsVerifyCode` 与 `CheckSmsVerifyCode`，验证码由供应商保管。当前阿里云账号的 100 条试用额度属于另一产品“短信服务”，其签名列表为空，个人账号无法直接用它实发。用户明确选择“号码认证 → 短信认证”，并告知已购买 1000 条该服务额度。叮咚因此调用 `Dypnsapi/SendSmsVerifyCode`，使用系统赠送签名“恒创联众”和登录注册模板 `100001`。这两个产品的额度独立；实发前仍核对账号真实可用量。

## 数据与接口

前端继续使用 `/api/v1/auth/sms` → `/api/v1/auth/login`，5 位数字输入不变。后端 `SMS_MODE=fixed_code|aliyun_verify`；真实模式随机生成 5 位码，HMAC 存入 `SmsChallenge.code_digest`，阿里云发送模板变量 `code`。模板参数同时包含 `min=5`。自定义验证码按号码认证 API 规则由调用方本地验证，因此不调用供应商的 `CheckSmsVerifyCode`；Seewow 使用供应商生成码，其校验方式不同。响应只给 challenge ID、有效期和重发间隔。仅中国大陆 `+86` 手机号进入阿里云发送。

发送期间为挑战预留不可登录状态（`sending`）；供应商返回成功后才设为 `sent`，失败设为不可用并清除摘要。限频锁在本地事务内完成，网络请求不持有数据库锁；同一手机号已有可用码仅在新码发送成功后失效。真实模式缺凭据直接报服务不可用，不静默使用固定码。供应商错误只映射成家长看得懂的文案，日志仅保留脱敏手机号、错误类别和请求 ID。

## 配置与交付

新环境变量使用叮咚独立命名空间 `ALIYUN_VERIFY_*`，密钥只落本机或服务器的受保护环境配置。仓库仅提交 `.env.example` 中的空占位与使用说明。部署时核对真实发送成功与应用端登录，运行环境显式切换真实模式；回滚可切回演示模式，但不能把演示固定码称为真实生产认证。
