## 三、稳定性

### S-07 `tests/flows.spec.js` 的「真实初始报告」用例本地必失败——根因是单线程 worker 排队，不是短信频控

- **现象**：`cd frontend && npx playwright test tests/flows.spec.js --reporter=list` → `1 failed / 7 passed (2.8m)`；失败用例「用途授权、22题、合成输入、真实初始报告」在 `expect(getByRole('button', {name:'查看初始报告'})).toBeVisible({timeout:20000})` 处超时。单独 `--grep "用途授权、22题"` 复跑同样 `1 failed (1.0m)`，可复现、非偶发。
- **根因（读库取证，非产品缺陷）**：本次失败会话 `ee0a1775-bb24-4f19-9860-07fa67ae3e31` 的算法处理尝试 `created 23:12:05 / started 23:12:13 / succeeded 23:12:14`，报告 `created 23:12:14`——而样本提交发生在约 50 秒前。本地 Celery 是 `--pool=solo`（单线程），队列里还有 beat 的 `dispatch_pending` / `recover_assessments` 与成批 `sync` 任务（`walk-ops.json` 的 jobs 表同一时刻有大量「排队中 0 / 5」），所以「提交合成样例 → 报告就绪」被排到 20 秒窗口之外。**不是短信频控**：本轮 1 小时窗口内 SmsChallenge 共 27 条，未触 IP 50 条上限。
- **建议**：这是本地环境问题，不建议改产品代码；要么给该用例的报告等待放宽（它是环境相关的硬编码 20 秒），要么在本地跑之前确认 worker 队列空。留档供下一轮判断是否值得改用例。
- **证据**：`flows-run.log`、`flows-single-rerun.log`（逐字失败输出）；库内时间线见 report.md 的取证命令。
